## 1. Blockers and near-blockers (fix before launch, most before SP7)

Ordered by consequence. Each names the report where the evidence lives.

1. **Curator unpublish and profile deletion never reach ticketed events.** `reviewProfile`
   reject-from-approved and `deleteProfile` cascade gigs, series, and bookings but not `events`.
   A banned venue keeps selling tickets, the curator cannot cancel (cancel and refund require an
   approved profile), no admin event callable exists, and the T+1 sweep pays the banned account.
   `deleteProfile` on a rejected profile also wipes `private/stripe`, so settlement is blocked
   forever and buyer money is stranded. Found independently by four audits.
   (sp1 #1, #2; sp3 #1; sp5 #4; cross-cutting #1, #23.)
2. **Settlement transfers are sourced from a charge smaller than the transfer.** The musician's
   98% of the full base is created with `source_transaction` set to the settlement charge, which
   is only 65% plus fee. Stripe caps a sourced transfer at the charge amount; FakeStripe does not,
   so all 704 tests pass and every ordinary live settlement would charge the curator and never
   pay the musician. Verified in `paymentsSettlement.ts:707` and `stripeClient.ts:859-866`.
   (sp5 #1.)
3. **One webhook signing secret cannot serve both Stripe endpoint types.** Platform events and
   connected-account events (`account.updated`, `payout.*`) arrive from separate endpoints with
   separate secrets; the code accepts one. Whichever endpoint is registered second fails
   signature verification on every delivery. (sp5 #3.)
4. **No chargeback or dispute handling.** `charge.dispute.*` is recorded and 200'd. A dispute
   silently debits the platform: no ledger row, no alert, no delinquency, no transfer reversal.
   Applies equally to ticket orders. (sp5 #2, #14.)
5. **`deleteAccount` destroys a fan's valid future tickets** without refund or capacity release,
   leaves ghost attendee rows, and writes no audit entry; there is no Auth `onDelete` trigger, so
   a console deletion orphans everything the callable would have cleaned. (cross-cutting #2, #3;
   sp1 #10.)
6. **`tickets.orderId` field override drops the single-field index** that the refund-convergence
   transaction still queries at collection scope (`ticketing.ts:865`). Production-only
   `FAILED_PRECONDITION` after a Stripe refund has already succeeded. (rules F1.)
7. **Functions runtime is Node 20**, deprecated 2026-04-30, decommissioned 2026-10-30. Local dev
   is Node 24. Deploys stop working in under two months. (cross-cutting #4.)
8. **A captured ticket payment whose order never completes is never reconciled.** The sweep's
   deferred branch sees `succeeded` and only bumps a counter; the fan is charged and holds no
   ticket, with no alert. (sp6 #5.)
9. **Find musicians crashes on both platforms** once any booking completes for a musician who
   never saved booking info (`recomputeReliability` writes a summary-only projection; both grids
   dereference `rates` and `preferences` unguarded). (sp4 #1.)
10. **Geocoder fails open to the stub in production** whenever `GEOCODER_PROVIDER` is unset,
    writing hash-derived US coordinates and a wrong city onto world-readable docs with no error.
    (sp3 #2.)
11. **Push tokens leak across accounts on a shared device.** Nothing removes the token on
    sign-out, and the rule's `allow write` cannot express delete, so the client could not clean up
    even if it tried. (sp1 #6; rules F3; cross-cutting #10.)
12. **Verification-email dead end at the purchase moment.** Buying requires a verified email;
    neither client offers a resend, shows an unverified banner, or refreshes the token after
    verification. (sp1 #5.)
13. **A sole admin of an approved profile cannot delete their account in-product**, and the invite
    lifecycle (invite, roster, revoke, accept, transfer admin) has no client UI at all, so every
    band and venue is single-user in practice. (sp1 #3, #4.)
14. **The launch checklist's App Check plan would 500 every SSR public page.** `/@handle` and
    `/e/[eventId]` read Firestore and Storage from the Node server with the anonymous client SDK.
    (sp2 #1; rules F19.)
15. **Door scanner renders a network failure as red "Not valid"** and auto-dismisses in 1.5 s;
    the event reminder formats the time in UTC and calls same-day shows "tomorrow"; an abandoned
    pending order blocks the same fan from the seats they just held for up to 70 minutes with no
    buyer cancel. (sp6 #2, #3, #4.)
16. **A musician never learns an application is a whole-run commitment**, and neither the inbox
    nor the thread identifies the other party. (sp4 #2, #3.)
17. **Em dashes in shipped copy.** 17 user-facing constants in `packages/shared/src/messages.ts`
    (the money sentences both clients render verbatim and compare with `===`) plus roughly 200
    server `HttpsError` and notification strings, against a binding hard rule. Total census:
    1,608 in docs, 1,534 in code, 675 in tests. (design #1, #2; docs A4, section D.)
18. **Firebase config is hardcoded to the dev project** in three client files and the functions
    bucket default; a production build has no switch. (sp2 #9; cross-cutting #7.)
19. **Mobile fans cannot reach any event they have not already bought.** Discover and Search are
    coming-soon, there is no venue page on mobile, the artist page has no event rows, and
    `app.json` has no universal links. The buy screen has no production entry point. This is SP7's
    reason to exist, stated precisely. (sp6 #1; inheritance L01 to L04.)

## 3. SP7 brainstorm brief

### 3.1 The fan today

Mobile: the root redirects every account to the fan tabs (Discover, Tickets, Search, Account).
Discover shows "Your upcoming shows" from held tickets over a coming-soon block; Search is
coming-soon; Tickets is a real wallet (QR, address reveal, transfers, incoming offers); Account
has theme, sign out, delete, notifications. `/event/[eventId]` and `/artist/[handle]` exist but
are reachable only from a ticket row or a raw custom-scheme link nothing generates. There is no
venue page on mobile.

Web: no fan routes. Sign-in without `next` lands on `/dashboard`, which for a profile-less
account says "No profiles yet, create a profile". `/tickets`, `/e/[eventId]` (public SSR),
`/@handle` and `/@handle/shows` (public SSR) exist. Empty states point fans at `/gigs`, the
musician job board with budget ranges.

A fan cannot: find any event, artist, or venue without a link; follow anything; set a city or
name (display name defaults to the email local part and lands on door lists); open a venue on
mobile; deep-link from any ticket notification; transfer on web; resend a verification email.

### 3.2 What SP7 can build on today (no backend work)

- World-readable: approved `profiles` (whole doc), `gigs` in open, filled, or booked-closed,
  `events` in published or completed with their `tiers`, `handles` by get. Every list must pin a
  single public status.
- Indexes already built and unused by any client: `events(status, startsAt)` (the fan feed
  query). Also `events(curatorProfileId, status, startsAt)`, `events(lineupMusicianProfileIds
  contains, status, startsAt)`, `gigs(status, startsAt)`.
- Notification kind `ticket` with `refId = eventId` on every ticket event; nothing routes on it.
- `LAUNCH_TIMEZONE` formatters and day-boundary helpers on both platforms.
- The `GigCard` and `DateBlockRow` anatomies, the `Chip` and `StatusBadge` primitives, the
  event/ticket tone maps.

### 3.3 What does not exist (verified absent)

Follows, favorites, saved searches, alerts, popularity or activity signals, denormalized counts,
a genre or tag field on events, `doorsAt` or age restriction, city or geohash indexes on
anything, a musician city or geo field, `users.homeCity` set by any UI, posters persisted
anywhere a client can read, a public curator page on mobile, share affordances, universal links,
analytics, email, a search index of any kind, `titleLower` or search tokens on events, artist
linkage for standalone events (only promoted gigs populate an artist's upcoming events).

### 3.4 Rulings the brainstorm must make (docs disagree)

1. The fan Search tab: foundation puts search in sub-7, SP4 moved "full search" to sub-8. Proposed
   split: SP7 owns browse (structured lists and filters over existing indexes); SP8 owns text
   search, ranking, saved searches, and the directory rework.
2. The map: three docs say sub-7, the 9A spec says sub-8. Proposed: a fan event or venue map is
   SP7 only if SP7 accepts building a geohash first; the musician gig-browse map is SP8.
3. Event discovery feed: the SP6 spec says "sub-7/sub-8". Proposed: feed and lists are SP7,
   search is SP8.
4. Alerts: follow-driven notifications (an artist you follow announces a show) are SP7;
   query-driven alerts (saved-search hits) are SP8.
5. Web fan parity: foundation promised discover and tickets parity on web; 9A reconciled web fan
   surfaces as empty. Either build a web fan home or rule it out explicitly.
6. Messaging: promised in the foundation spec, unscheduled by SP4, unowned since. Decide a
   sub-project or post-v1, and remove the two coming-soon tabs if post-v1.
7. Product data exposures that SP7 will widen: are gig budget ranges public by design (rules F2)?
   Are exact per-tier sales counts public (rules F10, sp6 #17)?

### 3.5 What SP7 must include or it ships hollow

From the inheritance ledger section C1, the SP6 report section D, and the design constraint sheet:

1. A published-events feed on both platforms, and a fan home on web (or the explicit ruling that

## Method

Eleven general-purpose agents ran in parallel with disjoint scopes (one per sub-project, plus
rules, design and copy, docs, cross-cutting, and the inheritance ledger), each instructed to read
its files in full, verify every doc claim against code, cite `path:line`, skip items recorded as
conscious accepted exceptions unless the acceptance looked wrong, and write a report with
severity, category, failure scenario, recommended action, and proposed owner. The rules agent
used the `firebase-security-rules-auditor` and `firebase-firestore` skills; the design agent ran
antislop Mode 2 with `antislop`, `antislop-ui`, `antislop-copywriting`, and
`web-design-guidelines`. The controller ran every merge gate, read all eleven reports, and
re-verified the three headline claims by hand. Agents were forbidden from modifying the repo; the
only writes are the audit documents themselves.
